\chapter{Prefect Workflow Orchestration}
\label{ch:prefect}

\section{Overview}

Prefect 2.0 is used to orchestrate the entire ML pipeline, providing task scheduling, error handling, retries, and comprehensive logging.

\section{Prefect Architecture}

\subsection{Core Concepts}

\begin{itemize}
    \item \textbf{Flow:} A collection of tasks and their relationships
    \item \textbf{Task:} An individual unit of work
    \item \textbf{Run:} A single execution of a flow
    \item \textbf{Deployment:} A flow packaged with schedule and config
    \item \textbf{Work Queue:} A queue for distributing work to agents
\end{itemize}

\subsection{Task Dependencies Graph}

The Prefect pipeline follows an 8-task dependency graph. It starts with fetching Bitcoin data, which feeds into data validation. After validation, the pipeline splits into three parallel branches: feature engineering, data preprocessing, and data splitting. These branches converge at the training stage where classification, regression, and deep learning models train in parallel. After training, all models proceed to the evaluation task to compute metrics and compare with baselines. Finally, the evaluation results are passed to the versioning task which creates a timestamp-based version ID and saves the model artifacts to the registry. This structure minimizes execution time by running independent tasks concurrently while maintaining dependencies between sequential operations.

\section{Main ML Pipeline Flow}

The Bitcoin ML pipeline is a Prefect flow orchestrating 8 tasks with retry logic and comprehensive logging. The flow accepts a data path parameter (defaulting to \texttt{data/raw/bitcoin\_timeseries.csv}) and executes the following orchestrated sequence: fetch 365 days of Bitcoin data from CoinGecko with 3 automatic retries, validate data quality and completeness, engineer 49 technical indicators from price and volume, preprocess the data by standardizing features, split into 80/20 train/test sets preserving temporal order, train classification and regression models in parallel, evaluate all models on the test set to compute metrics, and finally version the best models with a timestamp-based identifier in the model registry. The entire flow completes in 18-30 minutes and returns version metadata and performance metrics.

\section{Task Specifications}

The pipeline consists of 8 tasks with the following specifications:

\textbf{Task 1: Fetch Data} connects to the CoinGecko API to download 365 days of Bitcoin historical price data. It has 3 automatic retries with 30-second delays between retries and a 5-minute timeout. Returns a pandas DataFrame with columns: timestamp, price, volume, market cap.

\textbf{Task 2: Validate Data} checks that the DataFrame is non-empty, contains no missing price values, validates that all prices are positive, and verifies chronological ordering. Returns a boolean confirming validation passed.

\textbf{Task 3: Engineer Features} computes 49 technical indicators from the price and volume data, including moving averages, RSI, MACD, Bollinger Bands, and volume-based metrics. Drops rows with NaN values and returns the feature matrix.

\textbf{Task 4: Preprocess} standardizes all features using StandardScaler to have zero mean and unit variance, handles any remaining missing values through interpolation, and returns both the preprocessed data and the scaler object for later transformation.

\textbf{Task 5: Split Data} performs a temporal train/test split preserving the time ordering (no shuffling). Uses an 80/20 ratio by default, splitting at a specific date rather than randomly. Returns separate training and test datasets.

\textbf{Task 6: Train Models} runs in parallel training classification (RandomForest, GradientBoosting, XGBoost, LSTM, GRU), regression (same 5 models), and deep learning models (LSTM, GRU, Prophet). Has 2 retries for out-of-memory errors and a 30-minute timeout. Returns a dictionary of model results with metrics.

\textbf{Task 7: Evaluate} computes accuracy, precision, recall, F1-score for classification and MSE, MAE, R² for regression on the test set. Compares metrics against baseline thresholds and detects data drift. Returns evaluation results.

\textbf{Task 8: Version Models} creates a timestamp-based version ID (e.g., v20251210T104812Z), saves model artifacts to disk, updates the manifest.json file with version metadata, and registers models in the model registry. Returns the version string.

\section{Error Handling}

\subsection{Retry Strategy}

Prefect tasks are configured with automatic retry logic to handle transient failures. Network timeouts and connection errors automatically retry up to 3 times with exponential backoff (increasing delays of 30, 60, 120 seconds). Model training tasks retry twice specifically to recover from out-of-memory errors. Each retry includes jitter (random 0-10 second delay) to avoid thundering herd problems. Tasks have configurable timeouts: data fetching has a 5-minute timeout, while training has a 30-minute timeout to accommodate longer computations.

\subsection{Exception Handling}

Connection errors, timeouts, and temporary network failures trigger automatic retries. Out-of-memory errors during model training trigger a retry with reduced batch size or fewer trees. Data validation errors (empty dataframe, missing critical columns) fail immediately without retries since retrying won't fix data issues. Model training errors retry once; if the second attempt also fails, the task is marked as failed and logged for investigation. All exceptions are logged with timestamps, stack traces, and context for debugging.

\section{Deployment Configuration}

\subsection{Deployment Modes}

The pipeline can run in three ways. \textbf{Local Execution} runs the Python script directly for development and testing, useful for quick iteration and debugging. \textbf{Prefect Server Mode} starts a local Prefect server that provides a web UI for monitoring, scheduling, and triggering runs. This mode supports cron-based scheduling and is suitable for small-scale production deployments. \textbf{Prefect Cloud Mode} uses Prefect's managed cloud service with advanced features like distributed execution, better scalability, and integration with other platforms.

\subsection{Daily Schedule}

The deployment is configured to run daily at 2:00 AM UTC to retrain models with the most recent Bitcoin data. This time window ensures Bitcoin market volatility is captured across all major trading sessions (Asia, Europe, America). The cron schedule `0 2 * * *` triggers at exactly 02:00 UTC every day, making versioned models available by 02:20 AM UTC. The job is tagged with "production" and "daily" for easy identification and filtering in logs and dashboards.

\subsection{Manual Trigger}

A second deployment configuration allows manual triggering of the pipeline at any time. This is useful for immediate retraining after significant market events, bug fixes, or when adding new models. Manual runs use the same code but bypass the schedule, allowing operators to trigger training on-demand from the Prefect UI or CLI.

\section{Monitoring \& Observability}

\subsection{Flow Runs Dashboard}

The Prefect Server provides a web user interface at \texttt{http://localhost:4200} showing comprehensive pipeline information. The dashboard displays flow run history with execution status (success/failed/running), task execution status for each run showing which tasks completed and which failed, complete execution logs for debugging, and performance metrics like task duration and resource usage.

\subsection{Logging}

Prefect uses structured logging where each task automatically logs its start, progress, and completion. Debug logs capture intermediate values (number of records processed, feature shapes). Warning logs alert to potential issues (missing values encountered, performance below baseline). Error logs capture failures (connection timeouts, model training errors) with full stack traces. All logs are timestamped and associated with specific flow runs and tasks for traceability.

\subsection{Notifications}

Prefect can send notifications when flows complete successfully, when tasks fail, when SLA violations occur (e.g., execution time exceeds threshold), and on custom events. Notifications are typically sent to Discord webhooks so the team receives immediate alerts about pipeline status.
